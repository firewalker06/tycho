# Inquiry answer recovery

Remote UI answers opt into `response_mode: answer_receipt`. Legacy CLI/TUI callers keep the existing answer path and full response. This change retains the full display response and the existing display read; Card789 owns that separate optimization.

An intent contains `client_request_id`, `intent_created_at`, `expected_server_id`, the destination agent and inquiry IDs, and the exact answer, feedback, attachments and start choice. Only a user actor can use it. The service checks server identity before it reads or changes acceptance. The store checks active resource visibility under its lock. An archived or unavailable resource cannot accept or restart work through this path.

The store saves a fingerprint, original inquiry, acceptance time, original ownership generation, input-history hash, run count, start decision and schedule stop IDs. Answer/feedback history, FIFO inclusion, ownership and the acceptance record share the existing file transaction. A matching replay precedes current inquiry and upload validation. A changed payload or inquiry cannot use the original ID. Input rejection is saved against the exact fingerprint; correcting input requires a new ID. Suspended, retired and stale inquiries cannot be accepted as new answers.

Start recovery compares the accepted input history, run count, inquiry and ownership. A persisted pre-spawn run with the intent ID is an attempted original dispatch; retry does not launch another process. `attempted` does not claim that native spawn completed. A newer run, user stop, inquiry or ownership change supersedes a pending start. Schedule recovery uses the existing effect result ledger and original stop IDs, under schedule-then-agent locks. It can recover a committed result but cannot resume a newer stop. User stop or newer inquiry/ownership also prevents applying an unfinished original effect.

The record limit is 128 intents per agent within seven days of client intent creation (with at most 60 seconds of clock lead). A full index refuses new intents without evicting live records. Expired intents cannot become new writes after pruning. Inquiry effect records in schedule state expire on the same window; other effect records are unchanged. A retry outside this window can remain unconfirmed; it must not be treated as a fresh answer. No private payload is stored in the receipt index.

The browser keeps one unresolved intent per agent in IndexedDB, with its destination path/URL/server identity and exact payload, including file bytes and form values. It saves before the first write. Reload/navigation and authentication errors do not create another intent or send automatically. Retry uses current credentials for the saved destination. Only a matching versioned acceptance or durable rejection resolves uncertainty. Empty/invalid bodies, mismatched results and unbound 404/409 errors retain the exact intent. A bound rejection keeps correction inputs and files. The UI shows the saved answer and Retry answer; it does not expose protocol fields.

This is a focused endpoint contract. It does not add generic mutation retries, alter composer receipts, redesign schedules, or promise recovery of arbitrary stale answers. Existing file transactions roll back handled failures; this change does not add a cross-file write-ahead journal for abrupt machine loss during answer acceptance.
