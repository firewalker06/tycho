# Multiserver Agents And Projects Plan

Status: implemented on `feat/multiserver-resources`.

## Outcome

Show agents and projects from the local Tycho server and every configured peer
in the same lists without making the UI wait for the slowest peer.

The UI-serving server remains the broker. It keeps a small in-memory catalog of
agent and project list payloads, refreshes each server independently, and returns
the latest catalog immediately. Detail reads and mutations always include an
explicit server key.

This replaces the current browser-global active-server model for Agents and
Projects. It does not replicate runtime state and does not turn Tycho servers
into a mesh.

## Product Contract

- Agents and Projects show local and peer resources together.
- Every row shows its owning server when more than one server is configured.
- Peer health is `online`, `offline`, `unauthorized`, or `loading`; stale data
  is tracked separately.
- One slow or offline peer never blocks resources from another server.
- Cached resources remain visible when a peer becomes unavailable and are
  marked stale.
- Opening or mutating a resource uses its `server_key`; there is no ambient
  mutation target.
- Settings, schedules, GitHub authentication, push configuration, server
  restart, and other server-level APIs remain local to the UI-serving server.
- Existing browser-local peer tokens remain browser-local.

## Non-Goals

- Replicating agent, project, schedule, or log state between servers.
- A global active server for the whole application.
- Cross-server schedules or schedule-daemon control.
- Aggregating setup, GitHub, push, logs, hidden settings, or response-style
  configuration.
- Persisting peer snapshots across broker restarts in the first version.
- Server discovery beyond the existing configured and ad hoc peer flows.

## Identity And Ownership

Agent and project keys are only unique inside one Tycho server. All client state,
routes, cache entries, selections, and mutations must use a composite identity:

```json
{
  "server_key": "office-mac",
  "key": "web-agent-20260729-103000-000001"
}
```

The browser keeps local resource keys unqualified for existing deep-link and
draft compatibility. Peer resources use `server_key/resource_key`, which is
collision-free against URL-safe local keys; every resource still carries the
structured `server_key` and raw `resource_key` fields used for requests.

Use structured fields in application state. A serialized cache or DOM key may
use `server_key:kind:key`, but code must not recover identity by splitting that
string.

Routes become server-qualified:

```text
/#agent/office-mac/web-agent-20260729-103000-000001
/#project/office-mac/web
```

Old unqualified routes continue to resolve against `local` during migration.
Push links generated by the local server should move to qualified routes.

## Resource API

### Peer Snapshot

Add a compact endpoint to every Tycho Remote server:

```text
GET /resources
```

Example response:

```json
{
  "schema_version": 1,
  "generated_at": "2026-07-29T10:30:00Z",
  "agents": [
    {
      "key": "web-agent-20260729-103000-000001",
      "name": "Web review",
      "project_key": "web",
      "status": "running",
      "running": true,
      "unread": false,
      "awaiting_input": false,
      "blocked": false,
      "scheduled": false,
      "updated_at": "2026-07-29T10:29:58Z",
      "summary": "Reviewing the pull request."
    }
  ],
  "projects": [
    {
      "key": "web",
      "name": "Web",
      "group": "Product",
      "status": "configured",
      "agent_count": 1,
      "unread_agent_count": 0,
      "running_agent_count": 1
    }
  ]
}
```

`RemoteService#resource_snapshot` must load agents once and derive both agent
and project counts from that result. It must use compact list payloads and must
not run Git metadata commands. Git status and diffs remain detail operations.

Agents and projects form one snapshot so project counts always match the agent
rows returned with them.

### Broker Catalog

Add a broker-only cached read:

```text
GET /servers/resources
```

Example response:

```json
{
  "schema_version": 1,
  "revision": 42,
  "generated_at": "2026-07-29T10:30:00Z",
  "servers": [
    {
      "key": "local",
      "name": "Local",
      "local": true,
      "status": "online",
      "latency_ms": 18,
      "last_checked_at": "2026-07-29T10:30:00Z",
      "last_success_at": "2026-07-29T10:30:00Z",
      "stale": false,
      "refreshing": false,
      "error": null,
      "agents": [],
      "projects": []
    }
  ]
}
```

This endpoint reads an immutable in-memory snapshot. It performs no peer
network calls, Git commands, agent polling, or config reloads before responding.
The broker adds `server_key` and display metadata from its own configured
directory; it does not trust a peer to declare its identity.

Add an asynchronous refresh trigger:

```text
POST /servers/:server_key/resources/refresh
```

The response is `202 Accepted`. The broker deduplicates an in-flight refresh for
the same server. For a browser-local credential, the request uses the existing
`X-Tycho-Remote-Server-Token` header only for that refresh job; the broker does
not persist the token.

The UI can therefore:

1. Read the cached catalog immediately.
2. Trigger local and peer refreshes without waiting for them.
3. Poll the cached catalog until its revision changes.

### Explicit Resource Routing

Replace ambient `apiPath()` routing with:

```javascript
resourceApiPath(serverKey, path)
```

Local resources use existing paths. Peer resources use server-qualified broker
paths:

```text
/servers/:server_key/agents/...
/servers/:server_key/projects/...
/servers/:server_key/attachments/...
```

The broker only forwards resource-owned routes:

- `/agents` and `/agents/:key/...`
- `/projects/:key/...`
- `/attachments/:id` and `/attachments/:id/blob`

Project skill discovery stays under `/projects/:key/skills/:agent`. Agent-scoped
pull request routes remain under `/agents/:key/pull-requests/...`.

Do not forward these peer routes:

- `/setup`
- `/settings/...`
- `/schedules/...`
- `/github/...`
- `/push/...`
- `/server/restart`
- global `/pull-requests`

Keep `/servers/:key/proxy/*` temporarily for old UI assets, then remove or
restrict it after the qualified resource routes ship.

## Broker Catalog

Add focused classes instead of expanding `RemoteService`:

```text
HQ::RemoteResourceCatalog
  owns immutable per-server snapshots and revisions

HQ::RemoteResourceRefresher
  performs bounded local and peer refresh jobs

HQ::RemoteClient
  continues to own authenticated HTTP transport
```

Create the catalog once in `RemoteServer`, not once per request. Protect catalog
replacement and in-flight state with a mutex. Readers receive a complete
snapshot and never observe a partially mutated hash.

Refresh jobs use a bounded worker pool. Initial defaults:

- maximum concurrent peer refreshes: `4`
- connect timeout: `0.5s`
- read timeout: `1.0s`
- agents: `2s` while any agent on that server runs, otherwise `10s`
- hidden page: `30s`
- failures: exponential backoff from `3s` to `30s`

Keep these values as named constants and expose the effective intervals in the
catalog response for browser scheduling.

Each server updates independently. A successful refresh atomically replaces
its agents and projects from the same snapshot. A failed refresh:

- records health, latency, error category, and check time;
- retains the last successful agents and projects;
- marks retained resources stale;
- increments the catalog revision;
- never clears another server's data.

Do not include raw exception messages, tokens, or credential-bearing URLs in
the browser payload. Log the server key, duration, result, and error category.

Adding or removing a server must reconcile the catalog immediately. A refresh
trigger also reconciles the long-lived catalog with the request's freshly
loaded `Registry`, which covers manual `hq.yml` edits without putting config
loading on the cached read path.

## Compatibility

Peers may be upgraded at different times. When `/resources` returns `404`, the
refresher may fall back to `GET /agents` and `GET /projects` for that peer and
mark it with:

```json
{"resource_mode":"legacy"}
```

The fallback still fetches only agents and projects. It must use the same
timeout, health, stale-data, and partial-failure rules. Remove the fallback
after the minimum supported peer version includes `schema_version: 1`.

Reject unsupported future schema versions without discarding the last good
snapshot.

## Remote UI Changes

Replace these global fields:

```text
activeServerKey
agents for one server
projects for one server
one failureCount for the active context
```

with:

```text
serversByKey
agents containing server_key
projects containing server_key
health and refresh state per server
route identity containing server_key
detail caches keyed by structured server/resource identity
```

Split the current monolithic refresh loop:

- `refreshResources` reads the cached catalog and triggers due server refreshes;
- `refreshLocalShell` reads local schedules and setup state on their own cadence
  or when their screens need them;
- detail loaders use the route's explicit server key.

Do not reload setup and schedules at the running-agent polling rate.

Replace global peer-token header selection with
`resourceHeaders(serverKey)`. Broker-local requests receive only the UI-serving
server token; peer resource requests receive only that peer's browser-local
token override.

Agents:

- Merge catalog agents into one searchable and sortable list.
- Preserve project grouping, but distinguish projects with the same key on
  different servers.
- Show a compact server label when multiple servers exist.
- Include server name in filtering and accessible row labels.
- Derive Now, unread, running, blocked, and awaiting-input groups from the
  combined agent list.

Projects:

- Keep projects in the existing Agents project ledger for the first slice; do
  not add another primary-navigation tab.
- Merge catalog projects into that ledger, including projects with no agents.
- Show server health and stale state without hiding cached projects.
- Open project detail using `(server_key, project_key)`.

Settings:

- Remove **Switch to** and **Active server** language.
- Keep Add server, Edit token, Remove server, and per-server health.
- Add **Refresh** for one peer and **Refresh all**.
- Keep the local server visibly identified as the broker.

Forms and mutations:

- Carry `server_key` through agent create, edit, clone, archive, prompt, stop,
  inquiry, attachment, and project update flows.
- Confirm the target server for destructive operations.
- Do not let a stale row silently fall back to local.
- For bulk archive, group requests by server and report partial results.
- Resolve relative attachment and download paths through the owning
  `server_key`.

Schedules and server-level screens:

- Keep schedules and schedule daemon state local.
- Show local scheduled agents in the combined agent list like other agents.
- Keep setup, response style, GitHub, push, logs, and restart bound to the
  broker without a server selector.

## Delivery Phases

### Phase 1 — Compact Local Resource Snapshot

1. Add `RemoteService#resource_snapshot`.
2. Add a compact `agent_list_payload`.
3. Reuse one agent load for agent rows and project counts.
4. Avoid Git metadata refresh in list payloads.
5. Add `GET /resources`.
6. Cover payload shape, visibility, and one-load behavior.

This phase should improve local list latency before adding fan-out.

### Phase 2 — Cached Broker Catalog And Health

1. Add the long-lived catalog and bounded refresher.
2. Add `GET /servers/resources`.
3. Add asynchronous per-server refresh routes.
4. Implement independent health, stale data, timeout, and backoff.
5. Support configured and browser-local peer tokens.
6. Add legacy peer fallback.
7. Reconcile catalog entries on server add, remove, and refresh.
8. Warm the local catalog after the server starts.

### Phase 3 — Combined Read-Only Lists

1. Replace active-server list refresh with cached catalog reads.
2. Add server-qualified identities and routes.
3. Render combined Agents, Now, and Projects views.
4. Show server ownership, health, loading, and stale state.
5. Preserve filter, sort, focus, disclosure, and scroll state as individual
   servers update.
6. Split resource polling from local setup and schedule polling.
7. Keep the old selector available only as a temporary compatibility fallback.

At the end of this phase, all servers appear together, but peer mutations may
still use the legacy proxy internally.

### Phase 4 — Explicit Detail Reads And Mutations

1. Add qualified agent, project, and attachment broker routes.
2. Carry `server_key` through route parsing, cache keys, forms, and actions.
3. Move all peer agent/project detail calls and mutations to qualified routes.
4. Add explicit destructive target confirmation.
5. Handle cross-server bulk actions as grouped partial operations.
6. Qualify local push links and old local-only routes.

### Phase 5 — Remove Global Peer Switching

1. Remove `activeServerKey`, active-server resets, and active-server headers.
2. Remove peer routing from the generic API helpers.
3. Remove **Switch to** UI actions.
4. Restrict or remove generic `/servers/:key/proxy/*`.
5. Update README, Remote Server documentation, screenshots, and the old broker
   plan to describe the combined model.

Extend `bin/remote-ui-smoke` with two fixture peers and verify:

- agents and projects from all servers share one list;
- duplicate keys open the correct server's resource;
- an offline peer shows stale/offline state without hiding online peers;
- polling preserves filter text, focused forms, details, and scroll state;
- prompt, stop, archive, attachment, and project actions reach only the owning
  peer;
- Settings has no global server switch;
- mobile rows keep their touch targets and do not overflow.

Run:

```bash
bundle exec ruby test/remote_server_test.rb
bin/remote-ui-smoke
bin/test
```

### Performance Acceptance

- `GET /servers/resources` does no synchronous peer or Git work.
- A cached catalog response has a local p95 below `50ms` in the smoke fixture.
- An offline peer does not delay rendering resources from online servers.
- Peer timeout is bounded by the resource-refresh timeout, not the generic
  five-second proxy timeout.
- At most one refresh per server runs concurrently.
- Running-agent state becomes visible within `3s` under normal connectivity.
- Idle agent state becomes visible within `10s`.
- Project membership and agent counts become visible within `10s`.
- Browser polling does not cause repeated Git status commands for list views.

## Rollout And Reversal

Keep the old proxy routes and unqualified local routes through Phases 1–4.
Ship the combined list behind one temporary capability check:

```text
GET /servers/resources returns schema_version 1
```

If catalog refresh causes regressions, the UI can fall back to the existing
single-server list without reverting the peer snapshot endpoint or catalog
code. Remove the fallback only after the two-peer browser smoke check and normal
single-server workflow both pass.

## Definition Of Done

- Agents and Projects display resources from all configured servers together.
- Each resource has explicit server ownership from list through mutation.
- Offline and unauthorized peers have independent visible health.
- Cached resources survive transient peer failures.
- No non-resource peer API is reachable through the new broker routes.
- List refresh never waits synchronously on every peer.
- Existing single-server behavior remains unchanged when no peers are
  configured.
- `bin/test` and the two-peer browser smoke check pass.
